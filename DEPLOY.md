# Размещение Psy Method App: Render + Neon Free

## Схема и стоимость

React-клиент и Express API работают в одном Node.js Web Service на Render (Frankfurt). PostgreSQL размещается отдельно в Neon Free. Компьютер исследователя можно выключать: участники открывают ссылки через интернет.

`render.yaml` создаёт **только web-сервис** на платном плане `0.5c-512mb` (0.5 CPU / 512 MB). PostgreSQL Render не создаётся. Ориентир — **$7/месяц за Render + $0 за Neon в пределах лимитов**, без домена, налогов и дополнительных расходов. Перед размещением проверьте [тариф Render](https://render.com/pricing).

По [текущим лимитам Neon Free](https://neon.com/docs/introduction/plans): 0.5 GB данных, 100 CU-часов вычислений и 5 GB исходящего трафика на проект в месяц. После 5 минут простоя вычислительный узел засыпает и автоматически просыпается при запросе. Первый запрос может выполняться дольше. Это тариф с квотами, а не гарантия бесплатной работы при любой нагрузке; следите за Usage в Neon.

## 1. Подготовить репозиторий

1. Используйте Node.js из `.node-version`.
2. Проверьте сборку из корня проекта:

   ```sh
   npm run deploy:build
   ```

3. Отправьте проект в GitHub, включая `render.yaml`, `.node-version` и все три `package-lock.json`. `.env`, `node_modules` и `dist` исключены из Git.
4. Подготовьте уникальные логин и пароль суперадминистратора. Секреты вводятся в панели Render, не в файлы репозитория.

## 2. Создать PostgreSQL в Neon

1. Зарегистрируйтесь в [Neon](https://neon.com) и создайте проект на **Free**.
2. Выберите регион **AWS Frankfurt / eu-central-1**, если доступен, либо ближайший к Frankfurt. Подключение из Render идёт через интернет с TLS, а не по приватной сети Render.
3. Выберите рабочую ветку проекта, базу (например, `neondb`) и роль владельца, способную создавать таблицы.
4. Откройте **Connect**, включите **Connection pooling**, скопируйте PostgreSQL connection string. В имени хоста должен быть `-pooler`.
5. Пример формата (не настоящие учётные данные):

   ```text
   postgresql://USER:PASSWORD@ep-EXAMPLE-pooler.eu-central-1.aws.neon.tech/neondb?sslmode=require&channel_binding=require
   ```

   Копируйте только URL, без команды `psql` и внешних кавычек. Сохраните параметры из Neon. В production сервер устанавливает `sslmode=verify-full`, чтобы проверять сертификат и имя сервера. Самоподписанный сертификат старой приватной БД Render больше не используется.

Создание проекта Neon и получение URL выполняются вручную: Blueprint Render не создаёт ресурсы Neon.

## 3. Разместить приложение в Render

1. Создайте аккаунт Render и добавьте способ оплаты для web-сервиса.
2. Откройте **New → Blueprint**, подключите GitHub и выберите репозиторий и ветку.
3. Render прочитает корневой `render.yaml`. Root Directory оставьте пустым. В списке создаваемых ресурсов должен быть **один web-сервис и ни одной БД**.
4. Заполните секреты:

   | Переменная | Значение |
   | --- | --- |
   | `DATABASE_URL` | Pooled URL из Neon Connect |
   | `SUPER_ADMIN_USERNAME` | Логин суперадминистратора |
   | `SUPER_ADMIN_PASSWORD` | Сильный уникальный пароль |

5. Нажмите **Apply / Deploy Blueprint** и дождитесь **Live**. При первом запуске сервер подключится к Neon, создаст таблицы и отсутствующую учётную запись суперадминистратора. Данные с локального компьютера автоматически не переносятся.
6. Откройте URL из карточки сервиса и проверьте:
   - `/api/health` возвращает `{"ok":true}`;
   - вход по адресу `/super-admin/login` и обновление этой страницы;
   - создание исследователя и вход под ним;
   - создание новой ссылки, прохождение всех 10 шагов, просмотр и экспорт результатов;
   - сохранность результатов после redeploy.

Ссылка `demo-token` на главной странице не создаёт тестового участника — используйте новую ссылку из кабинета исследователя.

Последующие push запускают автодеплой. Build command: `npm run deploy:build`; start command: `npm --prefix server run start`.

## Если Render уже был настроен со своей БД

`sync: false` запрашивает секрет при создании Blueprint, но не заменяет существующее значение при обновлении. В **web-сервис → Environment** вручную замените `DATABASE_URL` на Neon URL и выполните redeploy.

Если в старой БД есть результаты, сначала остановите приём новых ответов, создайте резервную копию и перенесите её в пустую Neon БД через прямые подключения и `pg_dump` / `pg_restore`. Затем переключите приложение и проверьте данные. Иначе приложение откроет новую пустую базу.

Удаление секции `databases` из YAML не означает удаления уже созданной БД Render и прекращения её оплаты. После проверки переноса отдельно проверьте старый ресурс в панели. Не удаляйте его до сохранения копии и проверки результатов в Neon.

## Настройки окружения и домен

- `NODE_ENV=production` задан в Blueprint; включает Secure cookies.
- `PORT` назначает Render, вручную задавать не нужно.
- `COOKIE_SECRET` генерируется Blueprint автоматически.
- Без собственного домена адрес сайта берётся из `RENDER_EXTERNAL_URL`.
- Для своего домена добавьте его в **Settings → Custom Domains**, настройте DNS по инструкции Render и дождитесь TLS. Затем задайте `CLIENT_URL=https://ваш-домен` без пути и завершающего `/`, выполните redeploy.
- `VITE_API_BASE_URL` оставьте незаданным: сайт и API используют один домен.
- Версия Node берётся из `.node-version`; удалите старый `NODE_VERSION` из панели, если он переопределяет файл.

## Health check и сон Neon

`/api/health` проверяет только работу HTTP-сервера и **не выполняет SQL-запросы**. Регулярные проверки Render не расходуют вычислительный лимит Neon и не мешают засыпанию БД. Успешный health check не доказывает доступность PostgreSQL: её проверяйте входом в приложение и просмотром результатов.

При старте сервер сначала инициализирует БД, затем начинает принимать HTTP-запросы. Соединение ожидается до 15 секунд с учётом пробуждения Neon. Пул ограничен пятью соединениями, неиспользуемые закрываются через 10 секунд. Автоматических повторов операций записи нет, чтобы не дублировать действия участника.

## Резервные копии и восстановление

Neon Free не заменяет независимую резервную копию. Во время исследования создавайте копию ежедневно и перед изменениями схемы; при ежедневном расписании могут быть потеряны результаты после последней копии. Автоматическое расписание в этом проекте пока не настроено.

1. Установите клиентские утилиты PostgreSQL версии не ниже серверной.
2. В Neon Connect отключите pooling и возьмите **прямые** параметры подключения для `pg_dump`. Используйте отдельный файл `~/.pg_service.conf` с секцией `[psy_neon_backup]` (host, port, dbname, user, `sslmode=require`) и `~/.pgpass` для пароля; ограничьте права обоих файлов командой `chmod 600`. Не помещайте их в репозиторий. Формат описан в [документации PostgreSQL](https://www.postgresql.org/docs/current/libpq-pgservice.html) и [документации файла паролей](https://www.postgresql.org/docs/current/libpq-pgpass.html).
3. Сохраните копию в отдельную папку, вне репозитория:

   ```sh
   pg_dump --dbname='service=psy_neon_backup' --format=custom --no-owner --no-acl --file='/путь/к/копиям/psy-method-YYYY-MM-DD.dump'
   ```

   Подставляйте новую дату/имя, чтобы не перезаписывать предыдущие копии. Храните историю хотя бы за 30 дней и вторую копию на другом носителе или в защищённом облачном хранилище. В iCloud допустимо копировать готовый dump.

4. Периодически проверяйте восстановление в **отдельную пустую тестовую БД**. Создайте для неё отдельную секцию `psy_neon_restore` в service-файле:

   ```sh
   pg_restore --dbname='service=psy_neon_restore' --no-owner --no-acl --exit-on-error '/путь/к/копиям/psy-method-YYYY-MM-DD.dump'
   ```

5. При аварии восстановите копию в новую БД, проверьте таблицы и результаты, затем замените `DATABASE_URL` в Render её pooled URL и выполните redeploy. Сохраняйте исходную БД до проверки восстановления.

Откат deploy в Render откатывает код, но не содержимое Neon. Bootstrap создаёт отсутствующие таблицы и не заменяет версионированные миграции. Экспорт результатов из кабинета не является полной резервной копией БД.

## Если запуск не удался

- `Missing env variable`: проверьте `DATABASE_URL` и оба секрета суперадминистратора.
- Ошибка подключения: проверьте пароль, ветку, адрес Neon, состояние проекта и остаток квот в Usage. Не публикуйте connection string в скриншотах и логах.
- Ошибка TLS: используйте исходный хост Neon и не отключайте проверку сертификата.
- Health check успешен, но вход/результаты недоступны: проверьте Neon и журнал Render; health check намеренно не обращается к БД.
- Не найдены `tsc` / `vite`: используйте полную команду `npm run deploy:build`, она устанавливает devDependencies.
- `Client build missing`: нужна сборка из корня проекта, включающая клиент.
- Вход не сохраняется: используйте HTTPS, проверьте `CLIENT_URL` и отсутствие лишнего `VITE_API_BASE_URL`.
- Изменение `SUPER_ADMIN_PASSWORD` не обновляет существующую запись. Для ротации нужен отдельный сброс пароля в БД; redeploy сам по себе его не меняет.

## Локальная проверка

Скопируйте `server/.env.example` в `server/.env`, заполните переменные и используйте отдельную тестовую БД. Локально `NODE_ENV=development` позволяет работать по HTTP. Для локальной PostgreSQL используйте URL без SSL-параметров; для Neon сохраните SSL-параметры из Connect.

```sh
npm run deploy:build
npm --prefix server run start
```

Для просмотра собранного сайта задайте `CLIENT_URL=http://localhost:3001` и откройте этот адрес. Для разработки с Vite оставьте `CLIENT_URL=http://localhost:5173` и запускайте `npm run dev` из корня после установки зависимостей.

После сборки можно запустить проверки без реальной БД: `node --test server/tests/deployment.test.cjs`. Они проверяют отсутствие SQL-запросов в health check и обязательную проверку TLS в production. Реальное подключение к Neon и полный цикл участника проверяются после заполнения секретов и деплоя.
